# Microscope Software: Algorithm and Workflow Catalog

Prepared for software serving biotechnology, semiconductors, metallurgy, scientific research, optical device inspection, and adjacent industries.

Last reviewed: October 30, 2026.

## Scope and how to use this catalog

This is a broad planning catalog, rather than a claim to enumerate every microscopy method. It covers optical microscopy first, with extensions for electron, scanning probe, X-ray, and acoustic microscopy. Entries include individual algorithms, algorithm families, application analysis modules, and supporting software capabilities. End-to-end workflows are listed separately in Part II.

Each catalog entry gives a brief description and representative application areas. A family such as thresholding can support several selectable implementations. Application modules deliberately reuse the shared algorithms; for example, cell counting, inclusion counting, and wafer particle counting share detection and measurement infrastructure but need different recipes and validation.

The **Ref Link** column in the algorithm and workflow tables links to a representative application, worked example, or documented implementation. Related entries may share a resource when it demonstrates several methods.

For optical layouts, hardware requirements, open build resources, and a design mapping for all 57 workflows, see [Reference Microscope Designs](microscope_reference_designs.md).

**Input and hardware assumptions**

- Ordinary 2D images support many correction, segmentation, counting, and dimensional analysis methods. Physical measurements require calibrated pixel sizes and suitable image quality.
- Z stacks, time series, multiple channels, tiled acquisitions, spectra, diffraction patterns, and measured height maps carry different information; retain their axes, units, and acquisition metadata.
- Acquisition control requires compatible camera, stage, illumination, and instrument interfaces. Focus-derived height requires a calibrated Z axis and an appropriate sample surface.
- Interferometry, quantitative phase imaging, fluorescence lifetime imaging, Raman analysis, electron diffraction, and similar methods require their corresponding measurements or instrument configurations. They cannot be recovered reliably from arbitrary conventional images.
- Optical lateral resolution, axial resolution, localization precision, height precision, and measurement uncertainty are different quantities. Software must report the quantity actually measured.
- Quantitative analysis should retain raw data and record all corrections. Learned restoration, synthetic staining, and inferred structures need validation against independent measurements before their outputs are used quantitatively.

## Part III: Implementation planning

### A. Build shared foundations before specialized application packs

The following sequence is an engineering dependency suggestion, not a ranking of customer demand.

1. **Shared data and measurement foundation:** multidimensional data, calibrated coordinates, metadata, raw-data preservation, viewing, annotations, import/export, provenance, and basic quality scoring.
2. **Reusable analysis core:** correction, filtering, registration, segmentation, object measurements, editable results, batch recipes, and uncertainty-aware reporting.
3. **Acquisition layer:** device interfaces, synchronization, focus control, stage calibration, scan planning, coordinate relocation, and recoverable acquisition.
4. **Application packs:** biology assays; wafer and electronics inspection; metallography; optics and surface metrology. Give each pack its own controls, reference examples, reports, and validation criteria.
5. **Specialized modality integrations:** phase reconstruction, advanced fluorescence, spectral imaging, electron microscopy, SPM, X-ray, and acoustic analysis as compatible instruments and representative datasets become available.

### B. Use a consistent contract for each implemented module

| Module property | What to define |
| --- | --- |
| Purpose | The scientific or manufacturing question and the quantity the module reports. |
| Required inputs | Supported dimensions, modalities, data types, axes, units, metadata, and controls. |
| Hardware dependencies | Required sensors, actuators, illumination, timing, or specialized measurements. |
| Calibration dependencies | Reference data, configuration matching, validity interval, and uncertainty contributions. |
| Parameters and defaults | Meaning, units, valid ranges, sample-specific choices, and recorded overrides. |
| Outputs | Images, masks, objects, tables, maps, spectra, tracks, transforms, uncertainty, and quality flags. |
| Failure handling | Detectable invalid conditions, review requirements, fallback behavior, and recovery rules. |
| Validation evidence | Representative specimens, reference methods, sampling design, measured errors, and known limits. |
| Execution behavior | Expected memory, CPU/GPU needs, streaming support, chunk boundaries, and reproducibility. |
| Review and provenance | Links back to raw evidence, editable intermediate results, versions, and decision history. |

### C. Avoid common interpretation errors

- Keep presentation contrast changes separate from quantitative intensity data. Report the processing path used for each measurement.
- Treat fields, cells, tiles, and specimens as different sampling levels. Statistical replication should match the experimental question.
- Report 2D areas and section-derived grain sizes as such; use 3D measurements or justified stereology for volumetric claims.
- Validate line-width and edge measurements against the actual imaging modality. Subpixel fitting alone does not establish traceable accuracy or resolve arbitrary sub-resolution features.
- Specify measurement bandwidth, sampling, filtering, masking, and reference-form removal for roughness or edge-roughness results.
- Keep uncertainty and detection limits visible when converting images into physical or biological quantities.
- Evaluate learned methods on held-out specimens, batches, instruments, or sites appropriate to deployment; avoid leakage from neighboring tiles or related time points.
- Record the selected standard and edition for standards-based workflows. Generic algorithm support does not establish conformity to an entire test procedure.
